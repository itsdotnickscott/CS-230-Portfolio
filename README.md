# Briefly summarize The Gaming Room client and their software requirements. Who was the client? What type of software did they want you to design?
The Gaming Room developed a game called "Draw It or Lose It", where opposing teams will try to guess what an image is as it is procedurally "rendered" from a library of stock image photos. If a team fails to guess the answer to a puzzle, the other teams will get a chance to guess the answer for points.
The Gaming Room wanted their game to be offered on multiple operating systems, and it was our job to create a plan and execute it. In the end, a client-server architecture was decided on, where a server would be created on the Linux operating system, then a web frontend API will be developed so that users across all different types of platforms are able to access the game.

# What did you do particularly well in developing this documentation?
I particularly enjoyed, and did well, in researching the various operating platforms and deciding their various strengths and weaknesses for developing a server-side or client-side application. It was interesting to learn about the global market share of users on different platforms, as well as the different tools available for a developer on each. It led the way to creating my best recommendation for how the program should be structures using web APIs. On top of this, I think I identified how the storage and memory management with the application well. Diving tasks between the hard disk and RAM is important, and it will be important to balance the two, as a game application like this can't be too heavy on the memory.

# What about the process of working through a design document did you find helpful when developing the code?
By taking time to work through a design document before diving into the code, it ensures I've taken time in considering the primary goals and functionality asked by The Gaming Room. It gives a clear direction as to what is needed in the codebase. Without it, it would be more unclear what is expected by the client, and when the work for the project is complete. Additionally, it forces the developer to think about structure so that it has a clear purpose when implemented.

# If you could choose one part of your work on these documents to revise, what would you pick? How would you improve it?
I think my analysis of the UML Diagram could have been organized better. While I did cover all the information necessary, the order in which I wrote about the various classes and attributes could be confusing. For example, earlier bullet points would address classes that would not be talked about until later in the list. My analysis read like a developer's checklist, rather than an easy-to-read explanation that a non-coder could understand. Expanding on programming-specific terms would help any reader, such as business executives, to understand what is expected from the software structure.

# How did you interpret the user’s needs and implement them into your software design? Why is it so important to consider the user’s needs when designing?
As the client explained what was expected and needed, I would create a checklist of key words or phrases that were included in their description. I would then imagine myself as the user, a player, using the application and playing the game. It needs to be intuitive for the user to understand and use, as they are who the application is built for. If a user is unsatisfied with the product, it directly impacts the business in their goal to retain a customer base. It is important to consider that a user should have no idea about what is happening in the back end technically, so it is important for the developer to take extra measures so that it is easy and clear to use.

# How did you approach designing software? What techniques or strategies would you use in the future to analyze and design a similar software application?
The use of design diagrams, such as the UML Diagram, was extremely helpful in designing this software application. Making clear classes with specific, focused functionality will not only help the developer in staying organized while coding, but it will prove useful when addressing bugs and issues. Especially when working with teams, it is important for all team members to be on the same page as to how the program is designed, the relationship between various working parts of a project, and how they are expected to function. This allows multiple teams to work on one project simultaneously to create a working product. As a project manager, making sure teams are aligned would be through design documents such as this assignment, and diagrams to explain the functionality and structures of the application.
